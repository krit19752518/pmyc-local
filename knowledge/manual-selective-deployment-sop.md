# Football Manual Selective Production Deployment SOP

- Status: active operating procedure
- Last reviewed: 2026-11-02 (SAT Security one-file Production deployment)
- Scope: manually deploying an approved set of built Football runtime artifacts (prepared in an isolated Dev candidate worktree) to cPanel Passenger
- Authority: use with the root `AGENTS.md`, the Football Git/release standard, and the current release approval
- Automation: do not use deployment scripts; this procedure makes no Git push/fetch/merge, Production checkout update, Production `npm install`/build, or whole-directory synchronization. Any of those requires separate explicit approval and is outside this workflow.

## Non-negotiable rules

- Preserve the original dirty repository and all existing worktrees. Build and verify in a clean isolated worktree based on the approved source commit. Never reset, clean, stash, or bulk-copy files.
- Never inspect, stage, transfer, or modify `football/uploads/`.
- Treat these as separate identities: candidate source commit SHA, GitHub remote SHA, App Server checkout SHA, and SHA-256 for each actual Passenger runtime artifact. A selective release can be identified by a reviewed candidate commit and manifest without a push or checkout update; artifact checksums are not commit SHAs and do not claim the whole Production runtime matches that commit. Git `HEAD` does not prove what Passenger serves.
- Replace only the exact approved runtime paths. Preserve every other Production runtime file, including known pre-existing Git/runtime drift; do not normalize it as part of this release.
- Passenger startup may run DDL or backfill checks. A restart is not data-neutral. Do not run migrations or admin bootstrap as part of this SOP.
- PostgreSQL read-only checks run only on the DB Server, never on the App Server. Do not expose credentials in commands, logs, or evidence.
- Use fresh, explicit approvals for both gates below. Gate A covers staging and backup only. Gate B covers promotion, restart, verification, and rollback under the stated conditions.

## Standard preflight — complete once; continue directly when it passes

1. **Set release identity and scope.** Record purpose, full candidate commit SHA, exact source paths, exact built artifact paths, expected SHA-256 for every artifact, and the approved Production target paths. Confirm candidate ancestry/base and inspect the complete changed-path list from the repository root. Stop on any unapproved path, unexpected migration, or unexplained diff. Do not let unrelated commits in a range expand the deployment scope.
2. **Verify isolated candidate.** Confirm the Dev release worktree is isolated from active UAT/dirty checkouts and has no unrelated or unexplained changes. Intentionally prepared release changes are allowed when their source/commit/manifest identity and exact allowlist have been reviewed; do not reject a valid candidate merely because it contains those approved changes. Run the required focused and full tests, `npm run build`, `git diff --check`, and syntax checks on built JavaScript. Confirm every deployed `dist/` artifact is generated by that build and its SHA matches the release manifest. Failed or missing required checks block release.
3. **Inspect actual Production runtime read-only.** Confirm the Passenger entry point and runtime directory. Read current SHA-256, size, owner, and mode for each target artifact and the startup files needed for restart-safety review (`dist/app.js`, `dist/server.js`, `dist/adminAuth.js`, and `dist/db/initTables.js`, when present). Record App Server Git branch/`HEAD` and worktree state separately. Compare runtime to the approved baseline and candidate. Known drift outside the exact allowlist is preserved. If any pre-existing Production behavior in a target artifact is not represented in the candidate, or the runtime identity/path cannot be verified, stop for targeted reconciliation and approval; never overwrite it by assumption.
4. **Read-only DB baseline and restart preflight.** On the DB Server, record timestamped relevant row counts and release-relevant schema/table/column/type/index checks. Recalculate any startup backfill predicate and require zero pending rows. Confirm required schema is already present before any restart. Missing schema, nonzero pending backfill, changed startup artifact SHA, or unexplained count/integrity result is a stop condition; do not let restart create or repair schema/data. Counts can change during normal service use, so record values and investigate differences without modifying data.
5. **Prepare exact paths.** Use a release-ID-specific stage path and a fresh backup path beside the target on the same filesystem, for example:
   - Target: `/home/zbpzpszw/football_app/football/<approved-relative-path>`
   - Stage: `<target>.stage-<release-id>`
   - Backup: `<target>.backup-<release-id>-<timestamp>`
   Confirm available space and directory permissions read-only. Do not create the files before Gate A.

If all five checks pass, proceed directly to Gate A. Do not start a separate investigation phase without a failed, missing, or contradictory check.

## Gate A — Production staging and backup

Request explicit approval that names every artifact SHA, stage path, target path, and backup path. Gate A authorizes only upload to stage and creation/verification of the fresh runtime backup. It does not authorize promotion or restart.

After approval:

1. Upload only allowlisted built artifact files to their exact versioned stage paths. Do not sync directories or the repository.
2. Recheck each staged file SHA-256 against the candidate. Verify size, ownership, mode, and that stage paths do not alias the live targets.
3. Copy each current live target to its exact fresh backup path. Verify backup SHA-256 equals the immediately pre-copy live SHA and record metadata. Never treat an old backup or candidate copy as the current backup.
4. If upload, checksum, metadata, or backup verification fails, stop with target untouched. Do not continue to Gate B.

## Gate B — Atomic promotion, restart, verification, and authorized rollback

Once Gate A evidence is complete, present the exact stage/target/backup paths and SHAs, fresh DB/schema/backfill preflight, and startup runtime hashes. Request explicit approval covering atomic promotion, Passenger restart, HTTP/authenticated UI checks, read-only DB post-check, and rollback from the exact verified backup if required. Approval of Gate A is not Gate B approval.

After approval, immediately recheck candidate/manifest identity, live target SHA and metadata, staged SHA, backup SHA, startup artifact hashes, Passenger marker path, schema/index/type checks, zero pending backfill, and fresh DB counts. Stop before replacement if any differs from the approved evidence.

1. **Promote only the allowlisted file(s).** Use a same-filesystem atomic rename/replace for each exact target. Do not replace a directory or update Git checkout. Verify target SHA, size, owner, and mode immediately after promotion.
2. **Restart Passenger.** Repeat the startup safety check immediately before touching `/home/zbpzpszw/public_html/pmycfootball.in.th/tmp/restart.txt`. Restart only after required schema and backfill checks pass. Record timestamp and inspect startup/service errors; do not treat HTTP 200 alone as proof of successful initialization.
3. **Smoke-test.** Check the public homepage and relevant Admin/SAT login endpoints over HTTPS. With an already authorized session, inspect the affected Admin and role-specific UI behavior. Use read-only UI actions only: no status changes, delete, restore, or generated competition data. Record each result separately. If an authorized session is unavailable, mark UI verification unverified and the release partially verified.
4. **Post-check.** On the DB Server, repeat timestamped relevant counts and schema/index/type/backfill checks. Record differences; do not attribute normal count changes to the release without evidence. Confirm final live target SHA and startup artifact hashes.
5. **Rollback only under Gate B approval.** If a critical verification fails, first verify the exact backup path and expected pre-deploy SHA. Recheck startup safety before any rollback restart. Atomically restore only the corresponding approved target path; verify restored SHA/metadata, restart Passenger, and repeat HTTP/service checks. Never restore a broad directory or use an unverified backup. If backup or restart safety checks fail, stop and escalate without improvising.

## Stop conditions

Stop before the next write if the candidate, allowlist, runtime path/SHA, stage, backup, permissions, startup hashes, schema, backfill count, approval scope, or service health is missing, changed, or unexplained. Preserve evidence and existing runtime state. Do not broaden scope to repair drift, apply migrations, run database writes, or continue after a failed gate.

## Release evidence and closure checklist

Append one dated entry to `production-release-ledger.md` and update the Agent Brain release ledger according to `git-release-standard.md`. Include:

- purpose, candidate commit, candidate branch/worktree, exact artifact and target paths, allowlist, candidate/stage/live/backup SHA-256 values;
- actual Production Git `HEAD` and runtime identity separately, including known drift left unchanged;
- test/build/syntax/diff-check results and the exact changed-path review;
- Gate A and Gate B approvals and scope;
- backup path, SHA, metadata; promotion/Passenger restart timestamps and result;
- HTTP and authenticated UI results, including unavailable/unverified checks;
- timestamped DB pre/post counts, required schema/type/index findings, and pending backfill count;
- rollback path/results if used, and final outcome: `verified`, `partially verified`, `failed`, or `blocked`.

Call a release `verified` only when all required runtime, service, UI, and DB checks passed. Explicitly state any security mutation-path test not performed. A release may be operationally healthy and still be `partially verified` when authenticated behavior remains untested.
